## 概念澄清：正确的初始化顺序

- 用户提问：`git init → .gitignore → add` 与 `git init → add → .gitignore` 哪个对？答案：**前者**。
- 理由：`.gitignore` 是 `git add` 时刻的过滤器，规则先就位则被忽略文件从不进入索引；后者会导致 88 个构建产物被写入提交历史（`.git` 体积无法回落），且事后补规则仍被跟踪，需逐个 `git rm -r --cached`。
- 本仓库实际走的是正确顺序（先建 `.gitignore` 再 `git add -A`），所以构建产物从未进入历史。
- 第三种现实情况：仓库已有历史才想起加 `.gitignore` → 无法改顺序，只能「向前修复」（加规则 + 对已跟踪的 `git rm --cached`）；若已 push，清理历史需 `git filter-repo`/BFG + 强推。

## 实测记录：各类 `git add` 的暂存范围

- 统一初始状态（改 a.txt / 删 b.txt / 新增 c.txt / 新增被忽略的 noise.log），**在仓库根目录**执行：

| 命令 | 修改 | 删除 | 新增 | 被忽略文件 |
|---|---|---|---|---|
| `git add -A` | 暂存 | 暂存 | 暂存 | 不碰 |
| `git add .` | 暂存 | 暂存 | 暂存 | 不碰 |
| `git add -u` | 暂存 | 暂存 | 不动 | 不碰 |
| `git add a.txt` | 暂存 | 不动 | 不动 | 不碰 |

- **`-A` 与 `.` 的唯一差别是作用范围**（在 `sub/` 子目录里执行）：`git add .` 只暂存 `sub/s.txt`；`git add -A` 连根目录 `root.txt` 一起暂存；`git add -A .` 等同 `.`（pathspec 限定了范围）。Git 2.0 起 `-A` 不带 pathspec 即整个仓库。
- 关键性质：所有 add 形式都**尊重 `.gitignore`**（`-A` 的 all 指「所有变更」而非「所有文件」）；`-A` 只动索引不产生提交，`git reset` 即可撤销。
- 用户本仓库当前无「已跟踪但命中忽略」的文件，因此 `-A` 不会误吞那 88 个构建产物。
